# 코드 점검 2026-11-26 (v2.3.8)

v2.3.7 직후 이어서 한 점검. 지난 회차가 기능(Features) 쪽을 봤으므로 이번에는 **설정·곡 스캔 관리자**를 보고, 게임 없이 돌릴 수 있는 순수 계산을 떼어 내 **단위 테스트로 직접 확인**했습니다. 테스트를 붙이자마자 아래 1번 버그가 드러났습니다.

## 1. 버그: hwa 폴더 지문이 스캔과 변경 확인에서 서로 달랐음

**증상(추정 → 테스트로 재현).** CUSTOM 탭 진입 때 `CustomTrackManager.RefreshIfChanged`는 폴더 지문을 다시 계산해 지난 스캔 값과 비교합니다. 지문에는 곡 폴더 **자체의 수정 시각**이 들어 있었는데, 이 값을 부모 폴더 열거(`GetDirectories`)로 얻으면 Windows가 부모 색인에 늦게 반영한 값이 나옵니다.

| 출처 | 하위 폴더 수정 시각(ticks) |
| --- | --- |
| 부모 열거로 얻은 `DirectoryInfo` | `639312742075333754` |
| 같은 경로를 새로 연 `DirectoryInfo` | `639312742075343743` (약 1ms 뒤) |

그래서 스캔(작업 스레드)과 나중의 변경 확인이 같은 폴더에 다른 지문을 낼 수 있었고, 그러면
- 아무것도 안 바뀌었는데 한 번 더 `'hwa' 폴더 변경 감지 → 다시 스캔`,
- 그 폴더의 폴더별 지문도 달라져 **증분 재사용이 깨져** BMS를 다시 해석했습니다.

**수정.** 지문 계산을 `Managers/HwaStamp.cs` 하나로 모으고(전에는 스캔과 변경 확인에 같은 공식을 따로 적어 둠), 폴더 수정 시각을 뺐습니다. 파일 추가·삭제·이름 변경·내용 수정은 파일 이름·크기·수정 시각 목록만으로 모두 잡힙니다. `HwaStampTests` 5건: 두 계산 방식 일치(5회 반복 안정), 제자리 수정·같은 크기 수정·새 곡 폴더 감지, 하위 폴더 정렬. 변경 확인 중 예외는 모두 잡아(전에는 맨 `catch`) `DebugLog`로 남깁니다(`GetTracks` Prefix 안이라 새면 CUSTOM 탭이 깨짐).

## 2. 버그: 큰 `MaxScore`에서 점수가 음수로 넘침

`config.txt`의 `MaxScore`는 0 이하만 막았습니다. `MaxScore=10000000000`처럼 큰 값이면 `(int)Math.Floor(점수 × MaxScore / 1,000,000)`이 int 범위(약 21억)를 넘어 **음수 점수**가 화면·역카운트다운에 나왔습니다(C#의 범위 밖 double→int 변환).

**수정.** `Managers/ScoreMath.cs`(순수 계산): `ClampMaxScore`(0 이하·NaN·무한대 → 1,000,000, 상한 10억), `Scale`/`Total`은 int 범위로 포화. 값을 고치면 `[Config] MaxScore=… 는 쓸 수 없어 …로 맞춤` 경고. `PlayAssist`의 두 계산이 이를 씀. `ScoreMathTests` 9건.

## 3. 보고 그대로 둔 것

- `BmsParser`는 `#STOP`(채널 09)을 무시해 곡 길이를 짧게 볼 수 있으나, 곡 끝 시점은 `max(차트 길이, 음원 길이)`라 실제 플레이에 영향 없음.
- `ModConfig.Int`는 `1.0` 같은 소수 표기를 기본값으로 둠(경고 없음). 판정바 모양 2개 키뿐이라 유지.
