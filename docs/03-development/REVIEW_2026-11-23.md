# 코드 점검 2026-11-23 (v2.3.2, 추가 점검 v2.3.3)

`mod/` 36개 파일 전체를 다시 읽고, 업데이트 내성의 남은 구멍과 매 프레임·매 노트 경로의 IL2CPP 호출을 정리한 기록입니다. 게임 실기는 돌리지 않았고 빌드·단위 테스트·오프라인 도구(`tools/sigcheck`)로만 확인했습니다.

## 1. 업데이트 내성: 인자 형식을 지정한 훅 대상의 시그니처 변경

### 문제

`[HarmonyPatch(typeof(X), nameof(X.M), new[] { typeof(A), typeof(B) })]`처럼 인자 형식을 지정한 패치는 업데이트로 대상에 인자가 하나 늘거나(`GotoPlayScene(ITrack, ELevels, EPlayStyle)` → `(…, bool)`) 형식이 바뀌면 `AccessTools.Method`가 `null`을 돌려 **그대로 빠졌습니다.** 인자 형식을 지정한 패치에는 필수 패치(`GetTracks`, `GotoPlayScene`, `MikazukiConverter.Parse`, `SoundModuleForFMOD.Play`)와 해금 패치(`ItemUnlockChecker.IsUnlocked`/`IsDLCUnlocked`, `ItemProvideModule.IsOwned`)가 들어 있습니다. 2026-11-20에 넣은 오버로드 자동 선택(`PickOverload`)은 인자 형식을 **지정하지 않은** 패치의 `AmbiguousMatchException`만 다뤘습니다.

### 수정

- `PatchSignatureCheck.PickChangedSignature`: 같은 이름 메서드가 **하나뿐**이고 그 메서드가 패치 인자 대조(`Check`)를 오류 없이 통과할 때만 고릅니다.
  - 같은 이름이 여럿이면 고르지 않습니다. 지정했던 오버로드만 사라지고 뜻이 다른 형제가 남은 경우일 수 있습니다(예: `Resume(channel)`이 없어지고 `Resume(time, channel)`만 남음).
  - 패치가 받는 값 형식이 바뀌었으면(`int` → `long`) 대조에서 걸러져 고르지 않습니다.
- `PatchSignatureCheck.SameNameMethods`: 후보 모으기(기반 형식까지)를 부팅 해석과 `tools/sigcheck`가 함께 씁니다.
- `PatchResilience.ResolveDeclaredTargets`: 정확한 대상이 없으면 위 함수로 고르고 `ManualTargets`로 직접 붙입니다(Harmony의 속성 해석은 같은 대상을 다시 못 찾으므로). `[Harmony/Resolve] … (A, B)가 없음(업데이트로 시그니처가 바뀜) — …` 경고를 남깁니다.
- `PatchResilience.FallbackResolved`: 이번 부팅에서 대체 경로(오버로드 고름, 바뀐 시그니처 고름, `ResolveMethod`의 이름·인자 개수 대체)로 대상을 정한 패치 수. Harmony가 `TargetMethod`를 다시 불러도 두 번 세지 않습니다(경고 문구 중복 제거와 같은 집합).
- `UpdateGuard.ReportPatchSummary`: 대체 해석이 하나라도 있으면 패치가 전부 붙었어도 "정상" 대신 `패치는 전부 붙었지만 N개는 업데이트로 바뀐 대상을 대체 해석으로 찾았습니다` 경고를 냅니다. 붙기는 했어도 뜻이 같은지는 실기로만 알 수 있기 때문입니다.
- `tools/sigcheck`: 같은 해석을 오프라인으로 재현하고 `시그니처변경` 줄과 요약의 `바뀐 시그니처로 고름 N`을 출력합니다.

### 검증

- xUnit 71 → 74건: 인자가 늘어난 메서드 고름, 형제 오버로드·값 형식 변경·이름 삭제 거부, 기반 형식 탐색.
- `tools/sigcheck`(빌드 `26455233`): 통과 114, 오류 0, 경고 0, 대상 미확인 4(클로저 콜백), 오버로드로 고름 0, 바뀐 시그니처로 고름 0 — 현재 빌드에서는 대체 해석이 일어나지 않음(동작 변화 없음).

## 2. 병목: 매 프레임·매 노트 경로의 Unity 객체 null 비교

`UnityEngine.Object`의 `==`/`!=`는 인터롭의 `op_Equality`(→ `il2cpp_runtime_invoke`)라 값 형식 헬퍼와 같은 비용이 듭니다([IL2CPP_PITFALLS.md](IL2CPP_PITFALLS.md) 2장).

| 곳 | 전 | 후 |
| --- | --- | --- |
| `Overlay.Begin` | 매 프레임 `_root == null` + `localScale` + `Screen.width/height` (IL2CPP 4회) | 30프레임마다 한 번(창 크기 변경은 최대 0.5초 늦게 반영) |
| `Overlay.Rect`/`Label`/`End`/`HideAll` | 호출마다 `_root == null` (키뷰어를 켜면 프레임당 약 50회) | 관리 플래그 `_ready` |
| `JudgmentBar.GetShapeSprite` | 모양 4개마다 `cached != null` | `is not null` (스프라이트는 `DontUnloadUnusedAsset`, 직접 지울 때만 없어짐) |
| `JudgmentBar.RegisterHit` | 판정마다 라벨 문자열 생성 | 그릴 때 바뀐 경우에만 생성 |
| `CustomNoteSkin` 스폰 Postfix | 노트마다 `__result == null` | 두 기능이 꺼졌으면 바로 반환, 아니면 `is null` |
| `RandomNoteSkin.OnNoteSpawned`/`Copy` | 노트마다 `ui == null`, 이미지마다 `dst == null` | `is null` (이번 플레이에서 받아 둔 객체) |
| `NoteEffects.OnFrame` | 매 프레임 `_renderer != null` | `is not null` |
| `CustomJackets.ApplyListThumbnail` | 목록 행마다(스크롤 중 행당 2회) `thumbnail` 필드 읽기 + Unity null 비교 2회 | 공식 곡 행은 곡 ID 기록·사전 조회만, 커스텀 자켓이 있을 때만 `thumbnail` 읽기 |

파괴됐을 수 있는 객체(씬 전환을 넘는 것)는 여전히 경계에서 Unity 비교를 합니다. 오버레이 캔버스는 `DontDestroyOnLoad`라 실제로 파괴되지 않지만, 누가 파괴하면 최대 30프레임 동안 그리기 예외가 나고(`Core.OnLateUpdate`가 한 번만 경고) 다음 확인에서 다시 만듭니다.

## 3. 감사했지만 고치지 않은 것

- `NoteEffects.Factor`(속도 카오스, 노트별): 노트마다 `note._tickData` 래퍼를 만듭니다. 원시 필드 오프셋으로 읽으면 없앨 수 있지만 오프셋 검증이 필요해 이번에는 두었습니다(기능이 켜졌을 때만 동적 패치로 붙음).
- `FinishProcessor.UpdatePatternTime` Prefix(매 프레임): 커스텀 곡이 아니면 바로 반환하고, 같은 인스턴스·같은 길이는 캐시로 끝나 추가 비용이 없습니다.
- `CustomAudioManager.ApplyVolumes`: 장면 전환 페이드 동안 `set_CurrectionVolume`마다 채널별 `GetVolume` 1회. 페이드 중에만 불려 두었습니다.
- `OfflineBypass`·`LambdaTranslator`·`IcfScanner`·`PatchPreflight`: 2026-11-19~22 점검 이후 바뀐 것이 없고 매 프레임 경로가 아니어서 이번 변경 없음.

## 5. 추가 점검 (v2.3.3)

전 파일을 다시 훑어 매 프레임·매 노트 경로(`Core.OnLateUpdate`, `PlayAssist`, `KeyViewer`, `JudgmentBar`, `NoteEffects`, `CustomAudioManager`)와 업데이트 감지(`UpdateGuard`, `BuildFingerprint`)를 봤습니다.

| 분류 | 발견 | 조치 |
| --- | --- | --- |
| 업데이트 내성 | 지문이 게임 파일만 봐서, MelonLoader/Il2CppInterop을 올려 인터롭 어셈블리가 다시 만들어져도 "이 PC 실기 확인" 기록을 그대로 이어받음 | `loaderVersion` 키(위험 변경). 옛 기록에 없으면 `SameBuild`·`Diff` 모두 건너뛰는 **선택 키**라 이번 모드 업데이트만으로 기존 확인이 사라지지 않음 |
| 업데이트 내성 | `GetTracks`는 `"CUSTOM"`을 대소문자 무시로 보는데 `GotoPlayScene`(`track.Category ==`)·`LoadData`(`Contains`)·`GetSelectableCategoty`(`==`)는 정확히 비교 | 셋 다 `OrdinalIgnoreCase`. 어긋나면 커스텀 곡이 공식 곡 경로(FMOD 뱅크 조회 → 로딩 멈춤)로 가거나 탭이 둘 생길 수 있었음 |
| 병목 | `CustomNoteSkin.Apply`가 풀 노트마다 `target == null`·`sprite == null`·`img != null`(IL2CPP `op_Equality` 3회) | 관리 비교(`is null`). 방금 읽은 인터롭 값이라 파괴된 객체가 아님 |

감사했지만 고치지 않은 것:
- `JudgmentBar.RegisterHit`의 `Time.time`(판정마다 icall 1회): `runtime_invoke`가 아닌 내부 호출이라 비용이 작고, 지난 프레임 시각을 쓰면 1.5초 페이드 기준이 한 프레임 어긋나 두었습니다.
- `KeyViewer.TryBindLabels`의 `FindObjectOfType`: 바인딩 전 최대 2초 동안 10프레임마다만 불립니다.
- `PlayAssist.IsPlaying`(`CurrentJudge != null`): `JudgeProcessor`는 `UnityEngine.Object`가 아니라(`dump.cs` TypeDefIndex 3054) 관리 비교입니다.

검증: Release/Debug 빌드 경고·오류 0, xUnit 77건, `tools/sigcheck` 통과 114·오류 0·경고 0·대체 해석 0, `tools/lambdascan` `ALL PASS`. **실기 미실행** — 다음 부팅에서 `[UpdateGuard]` 지문 줄에 `loaderVersion`이 처음 기록되는지(`UserData\SixtarGateMod.BuildState.txt`)와 `업데이트 점검 결과: 정상`이 유지되는지 확인.
