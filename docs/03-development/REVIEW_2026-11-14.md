## 2. 람다 기계어 대조: 바이트 단위 → 명령 단위 (`Managers/X64Decoder.cs` 새 파일, `NativeLambdaScan.cs`)

**문제:** 11-12에 넣은 엄격 모드(레지스터 추적)는 바이트를 하나씩 밀며 64비트 `mov`만 골라 읽었습니다. 그래서
- 다른 명령의 변위·즉값 안에 든 `48 8B 41 18` 같은 바이트를 `mov`로 잘못 읽을 수 있었고,
- `lea`, `xor`, `pop`, 32비트 `mov`, 그리고 `call`(호출 규약상 rax·rcx·rdx·r8~r11을 덮음)이 클로저·소유자 레지스터를 덮는 것을 몰랐습니다.
  실제 BGA 람다(`0x654C40`)가 이 모양입니다: `mov rbx, rcx` → `lea rcx, [rip+…]` → `call` → `mov rax, [rbx+0x18]`. 지금은 rbx를 쓰니 맞았지만, 업데이트 후 rcx를 다시 쓰는 모양이 나오면 덮인 rcx를 클로저로 보고 거짓 Hit을 낼 수 있었습니다.

**수정:** 최소 x64 명령 길이 해독기(`X64Decoder`, IL2CPP 의존 없는 순수 함수)로 명령 경계를 따라 걸으며, 명령마다 어느 범용 레지스터에 쓰는지 보고 소속을 지웁니다. `call`은 휘발 레지스터를 모두 지웁니다. 모르는 명령을 만나면 추측하지 않고 그 자리에서 멈춥니다(그러면 결과가 Inconclusive/OwnerOnly가 되어 기존대로 느슨 모드로 넘어감). 느슨 모드는 바꾸지 않았습니다.

**시험 (`tools/lambdascan`):**
- 실제 바이너리 30건 + 합성 5건(기존 35건): 수정 전후 판정 동일, 모두 통과.
- 새 합성 5건: `lea`가 rcx를 덮음, `call`이 rcx를 덮음, `call`을 넘어 rbx에 남은 클로저, `xor ecx,ecx`, 즉값 안의 `mov` 바이트. **수정 전 스캐너는 이 중 4건에서 Hit(오판)**, 수정 후 모두 기대대로.
- **capstone 대조:** 새 `tools/lambdascan/capstone_lengths.py`가 `script.json`에서 이름에 `b__`·`MoveNext`가 든 함수 6,021개의 앞 192바이트를 capstone으로 해독해 명령 길이를 적고, lambdascan이 `X64Decoder` 길이와 비교 → **명령 188,398개, 길이 다름 0, 미지원 0**.

```
python -I tools\lambdascan\capstone_lengths.py "<게임>\GameAssembly.dll" il2cpp_dump\script.json caplens.txt
dotnet run --project tools\lambdascan -- "<게임>\GameAssembly.dll" caplens.txt
```

## 3. `FindMethodInType`도 번역 사전에 (`LambdaTranslator.TranslateMethodInType`)

`GotoPlayScene` 번들 콜백과 같은 클로저의 TextAsset 패턴 콜백(`b__14`)은 `PatchResilience.FindMethodInType`이 사전 밖에서 매번 찾았고, 이름 문자열을 `PadLeft(64)`로 정렬했습니다. 이제 다른 람다와 같은 사전에 들어가 RVA 대조·`how` 기록·안 쓰는 항목 정리를 받고, 람다 번호로 정렬합니다. 사전 키는 클로저 이름(업데이트로 바뀜) 대신 바깥 형식 이름을 씁니다. 그래서 번역 항목이 9개 → **10개**가 됐습니다(새 항목 `0x7EB400`).

같이 정리: 접두사 비교(`_M_b__` / `<M>b__`), 람다 번호 읽기, 번호 정렬, "순서로 고른 항목" 경고를 함수 하나씩으로 묶어 중복 제거. 안 쓰게 된 `PatchResilience.ParametersMatch` 삭제.

## 4. 업데이트 내성: 사전 JIT 검사 (`Managers/PatchPreflight.cs` 새 파일)

**문제:** 게임이 업데이트되면 MelonLoader가 인터롭 어셈블리를 새로 만듭니다. 모드가 쓰던 필드·메서드·속성이 없어져도(이름 변경, 형식 변경) 모드 DLL은 그대로 로드되고 Harmony 적용도 성공합니다. 문제는 그 Prefix/Postfix가 **처음 불릴 때** JIT에서 `MissingFieldException`/`MissingMethodException`이 나는 것이고, IL2CPP 트램펄린이 이를 잡아 `During invoking native->managed trampoline` 오류만 남긴 채 게임은 계속 갑니다(예: 판정 훅이면 노트마다 실패).

**수정:** 패치 적용 전에 각 패치 클래스(중첩 형식 포함)의 모든 메서드와, IL의 `call`/`callvirt`/`newobj`/`ldftn`을 따라가 닿는 모드 내부 메서드(도우미, 람다 본문)를 `RuntimeHelpers.PrepareMethod`로 미리 JIT합니다. 실패하면 그 패치를 붙이지 않고 `[Harmony/Preflight] '패치' 건너뜀: … — 메서드: 예외` 오류를 남기며, `[CriticalPatch]`면 "필수 패치 빠짐"도 냅니다. `NoteEffects`의 동적 훅 2개도 붙이기 직전에 같은 검사를 합니다.

**시험:**
- 실험(.NET 6, scratchpad): 라이브러리에서 필드·메서드·정적 속성을 지운 뒤 PrepareMethod → 각각 `MissingFieldException`, `MissingMethodException`, `MissingMethodException(get_…)`. 멀쩡한 메서드는 통과.
- `PatchPreflight.cs`를 그대로 컴파일한 시험: 사라진 멤버를 직접 쓰는 패치, 도우미를 거쳐 쓰는 패치, 람다 안에서 쓰는 패치를 모두 잡고(실패 위치로 `Helper.Touch` 등 정확한 메서드를 보고), 멀쩡한 패치는 통과.
- 실기: 120개 모두 통과(거짓 실패 0), 메서드 435개, 54ms.
